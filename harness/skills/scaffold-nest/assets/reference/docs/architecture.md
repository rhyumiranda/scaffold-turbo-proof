# Architecture

`src/app.ts` composes `ProjectsModule`, `PlatformModule` and the rate limiter. `src/main.ts` initializes telemetry before loading application modules and owns process termination.

Authentication is a global guard: new endpoints fail closed unless deliberately marked Public. Only health checks are public in this reference. Object authorization remains inside the feature's owner-scoped operations; being authenticated alone never grants another user's record.

`src/projects/` owns controller, input/output DTOs, application operations, its repository and its module, plus its data in `prisma/schema/projects/`. Its public index exports the module and the service; the repository stays private. Controllers translate HTTP; services decide owner-scoped reads and conditional writes; the repository is the only code that touches the module's Prisma models. `src/platform/` owns identity, the database connection (pool, Prisma client), config, health, request deadlines, logs and telemetry. Platform never imports a feature.

The TypeScript-AST architecture check resolves local imports/exports, rejects private cross-module imports, direct feature database/transport dependencies, computed imports and cycles. It also enforces data ownership (below). Negative fixtures in `test/architecture.unit.test.mjs` prove these failures. New path aliases or execution systems require extending the checker, not bypassing it.

Database access uses Prisma ORM 7 (`prisma-client` generator, output `src/generated/prisma`, generated by `prisma generate` inside `build` and `typecheck`; never committed). The client runs on the `@prisma/adapter-pg` driver adapter over one `pg` pool that platform owns, so there is no Rust query engine and the pool settings below are the whole budget. Every Prisma operation runs in one `postgres.query` span; connection loss, timeouts and pool exhaustion become 503 with `Retry-After`. Related multi-statement business writes need an explicit transaction (`$transaction`) before that feature is added; this example uses single-statement atomic writes. Rename uses `updateMany` filtered by id, owner and version, then returns the validated id/name and incremented version without a second query; ordinary resource reads still return `createdAt`. A pool has at most five connections; aggregate replicas and migration processes when setting the server budget.

HTTP header arrival is bounded by five seconds, body arrival by ten seconds, and application middleware enforces one six-second budget from receipt of headers through response. Within that budget, JWKS is two seconds, PostgreSQL statements three seconds, client query waits four seconds, and controller work at most five seconds or the remaining budget. A timed-out mutation may have committed: never automatically replay it. HTTP cancellation does not promise SQL cancellation; PostgreSQL's statement timeout bounds remaining work.

OpenAPI is generated from explicit Swagger DTOs and errors. `contract:check` checks integer semantics and response-schema validation; integration tests validate actual success/error bodies. `contract:compat` compares existing operations to the last reviewed accepted schema, resolving references. It intentionally rejects semantic changes even if some are backward-compatible, while allowing new endpoints. Unsupported cyclic/external references fail closed and need a reviewed checker upgrade. It is a conservative compatibility guard, not a complete OpenAPI semantic-diff engine.

## Data ownership (modular monolith)

Each feature module owns its data. The Prisma schema is split into files (`prisma.config.ts` points `schema` at the `prisma/schema` folder):

- `prisma/schema/base.prisma`: the `generator` and `datasource` blocks only, never a model.
- `prisma/schema/<module>/*.prisma`: the models of `src/<module>/`. `prisma/schema/projects/projects.prisma` holds `Project`.

Rules, all enforced by `check:arch` (`scripts/check-architecture.mjs`) and proven by `test/architecture.unit.test.mjs`:

- A module reads and writes only its own models (`<client>.<model>.<operation>` with another module's model fails), and only platform may import the generated client, `@prisma/client`, `@prisma/adapter-pg` or `pg`, or run raw SQL (`$queryRaw` and friends).
- A module's repository stays private: its `index.ts` exports the service. Another module that needs project data calls `ProjectsService`, never the repository or the `Project` model.
- No foreign keys anywhere. The datasource sets `relationMode = "prisma"`, so a relation between two models of the same module creates no `FOREIGN KEY`; such a relation needs an `@@index` that starts with its scalar fields. Across modules there are no Prisma relations at all, only plain ID columns (like `owner_id`, which holds the identity provider's subject). Any migration SQL containing `FOREIGN KEY` or `REFERENCES` fails `check:arch`, and `test/migrations.test.mjs` proves the migrated database has zero foreign-key constraints.
- Integrity rules stay in the database inside a module: primary key, `NOT NULL`, length/trim/version `CHECK` constraints, the `version` column and the `projects_owner_order` index. The Prisma schema cannot express `CHECK` constraints, so they are written into the migration SQL by hand, next to the generated statements.

### Adding a module's data

1. Create `src/<module>/` (module, service, private repository) and `prisma/schema/<module>/<module>.prisma` with that module's models. Reference other modules' records by plain ID columns only.
2. Generate the SQL with `prisma migrate diff`, never by applying changes to a database: the first migration uses `npx prisma migrate diff --from-empty --to-schema prisma/schema --script`; later ones use `--from-config-datasource` instead of `--from-empty`, with `DATABASE_URL` pointing at a disposable `_test` database that has every committed migration applied (the diff only reads it). Save the output as `prisma/migrations/<NNNN>_<name>/migration.sql` with the next number, wrap it in `BEGIN;` … `COMMIT;` (`prisma migrate deploy` runs a migration without a transaction, so without this a failing statement leaves the earlier ones applied; `check:arch` requires it), add `CHECK` constraints by hand, review it, and commit it with the schema file.
3. Apply it only through `npm run migrate` (it runs `prisma migrate deploy`). Never edit a migration once any environment applied it; add a new one. Never use `prisma migrate dev`, `prisma db push` or `prisma migrate reset`.
4. Run `npm run check:arch`, then `NODE_ENV=test npm run test:integration` on a disposable database: it also checks that the migrations produce exactly the Prisma schema (`prisma migrate diff --exit-code`).
